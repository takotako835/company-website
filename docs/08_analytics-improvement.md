# 08. アクセス計測・管理サイト・自動改善ループ

- 状態: **実装済み(2026年8月27日 承認・Phase 1〜4a 完了)**。稼働にはセットアップ(§8)が必要
- 目的: HP改善に使える数値を自前で取得・データ化し、管理画面で見える化し、分析→改善が回り続ける仕組みを作る
- 結論: **構築できる。** ただし「自動改善」は安全な範囲設計が肝心(§5)

## 0. 全体像

```
訪問者のブラウザ
   │ 計測ビーコン(1KBのJS・Cookieなし)
   ▼
本サイト /api/track (Astro SSR・既存のRenderサーバー)
   │ 匿名化して保存
   ▼
Supabase(データベース・無料枠)
   │                    │
   ▼                    ▼
/admin 管理画面      週次の自動分析(GitHub Actions → Claude API)
(パスワード保護)        │
                        ├─ 分析レポート(メール送付+管理画面に保存)
                        ├─ A/Bテストの勝者を自動採用(事前承認済みの案の中で)
                        └─ 改善案をPRとして提案(人が承認してから本番反映)
```

- 追加の月額費用: **ほぼゼロ**(Supabase無料枠・GitHub Actions無料枠・Claude API 約100〜300円/月)。サーバーは既存の Render Starter をそのまま使う
- vietnam-guidebook と同じ構成要素(Supabase・Render・Resend)なので、運用の勝手が揃う

## 1. なぜ GA4 ではなく自前計測か

| 観点 | 自前(第一者・Cookieなし) | GA4 |
|---|---|---|
| Cookie同意バナー | **不要**(個人を特定しない設計にする) | 要検討(06_seo §5 の懸念そのもの) |
| データの所有 | 自社DB。分析APIに直接渡せる | Googleの画面/API経由 |
| LINEタップ等の独自CV | 自由に定義 | 可能だが設定が煩雑 |
| 自動改善ループとの接続 | **同じDBなので直結** | API連携の実装が別途必要 |

GA4は後から併用も可能。まず自前計測を土台にする。

## 2. Phase 1|計測(取得する数値)

### イベント設計(最重要CVから逆算)

| イベント | 取得タイミング | HP改善に効く理由 |
|---|---|---|
| `pageview` | 全ページ表示 | PV・回遊・ランディング・参照元・UTM |
| `cta_line_click` | LINEボタンのタップ(全箇所・位置ID付き) | **最重要CVの代理指標**(LINE内の成約はサイト外のため) |
| `form_view` / `form_start` / `form_submit` | フォーム表示・入力開始・送信 | フォームの離脱点が分かる |
| `shindan_start` / `shindan_q{n}` / `shindan_result` | 診断の開始・各設問・結果(タイプ付き) | 診断ファネルの離脱点・タイプ分布 |
| `shindan_line_click` | 診断結果からのLINEタップ | 診断→CVの接続率 |
| `scroll_depth` | 50%/90%到達 | どこまで読まれているか |
| `vitals` | LCP/CLS/INP実測 | 実ユーザーの速度(06_seo §4の実地版) |

### プライバシー設計(誠実さのブランドに合わせる)

- Cookie・localStorageを使わない。訪問者の識別は「IP+UA+日替わりソルト」のハッシュのみ(**翌日には同一人物と突合できない**)。生IPは保存しない
- 個人情報(フォーム入力値)は計測に含めない
- プライバシーポリシー§5「アクセス解析」の記載は現状のままで整合。文言の微修正案は実装時に提示

### 実装

- ビーコン: `navigator.sendBeacon('/api/track', ...)` を Base.astro に約1KBのインラインJSで(追加ライブラリなし・表示速度に影響なし)
- 受け口: `/api/track`(既存の contact API と同じ作法。レート制限・UA判定でbot除外・Supabaseへ`service_role`キーで挿入。キーはサーバー環境変数のみ)
- テーブル: `events(ts, visitor_hash, session_id, path, type, meta jsonb, referrer, utm_*, device)` + 日次集計ビュー
- 保持期間: 明細90日・日次集計は無期限(Supabase無料枠500MBで十分)

## 3. Phase 2|管理サイト(/admin)

- 認証: `ADMIN_PASSWORD`(環境変数)+署名Cookieセッション。公開ページとは完全分離・noindex
- 画面構成:
  1. **サマリー**: 訪問数・PV・CV数(LINEタップ/フォーム送信)・CVR。前週比
  2. **ファネル**: 訪問→診断開始→完了→LINEタップ / 訪問→フォーム表示→送信(離脱率つき)
  3. **流入**: 参照元・UTM・ランディングページ別のCVR
  4. **ページ**: ページ別PV・滞在の代理指標(スクロール到達)・LINEタップ位置別クリック数
  5. **診断**: タイプ別分布・設問ごとの離脱
  6. **速度**: LCP/CLS/INPの実測分布
  7. **レポート**: 週次分析(Phase 3)のアーカイブ
- グラフはサーバー側でSVG生成(クライアントJS追加なし=本サイトの速度原則を管理画面でも維持)
- 週次サマリーは既存の Resend でメール送付

## 4. Phase 3|自動分析(週次)

- 起動: GitHub Actions の cron(無料)→ 秘密ヘッダー付きで `/api/analyze` を叩く
- 処理: 直近1週+前週の集計を取り出し → **Claude API(`claude-opus-5`)** に渡して分析
- プロンプトに**このリポジトリの規範を注入**する: 04コピールール・禁止事項(価格非掲載/実績創作禁止/煽り禁止)・ブランドトーン。分析AIが規範の外の提案をしない仕組みにする
- 出力(構造化): ①数値サマリー ②目立つ変化と仮説 ③改善案トップ3(対象ページ・変更案・期待効果・根拠) ④次週の観察ポイント
- 保存+管理画面に表示+メール送付
- 費用試算: 週1回・入出力合わせ約3万トークン → **月100〜300円程度**

## 5. Phase 4|自動で改善し続ける仕組み(2段構え)

「無人でどこまで任せるか」を線引きするのが設計の核心。

### (a) A/Bテスト+勝者の自動採用 — ここは完全自動にできる

- 対象: Heroの提供価値一文(既にA/B/C案が docs にある)・CTA文言・診断ボタン文言など、**事前に人が承認した候補の中から**配信
- 割り当て: 訪問者ハッシュで50/50(Cookieなし)。CV(LINEタップ/フォーム送信)を変種別に記録
- 判定: 最低サンプル数+統計的有意(95%)を満たしたら**勝者をDBフラグで自動採用**し、レポートで報告
- 安全な理由: 出せる文言は全て事前承認済み。自動なのは「どれを出すか」の選択だけ

### (b) AIによる改善提案 → PR → 人が承認 — 本番の書き換えは無人にしない

- 週次分析の改善案を、具体的なコード差分(PR)として GitHub に自動作成
- **マージ(=本番反映)は人の承認制**。承認すれば既存の自動デプロイで公開
- 無人化しない理由: 本サイトには法令・ブランド上の制約(価格非掲載、実績数値の創作禁止、特商法・プライバシーポリシーの整合、売り込み禁止のトーン)があり、公開文言の完全無人書き換えはこの制約に対する事故リスクが便益を上回る。**「提案の生成と検証まで自動・公開判断は人」**が最適点
- 発展形: 提案PRの生成を Claude の Managed Agents(定期実行)に載せ替えることも可能。まずは軽量な Actions + API で始める

## 8. セットアップ手順(これをやると稼働する)

### 8-1. Supabase(約5分)

1. https://supabase.com/dashboard → **New project**(名前: `maido-analytics` 等。リージョンは Tokyo)
2. 作成後、左メニュー **SQL Editor** → リポジトリの `supabase/schema.sql` の中身を貼り付けて **Run**
3. 次の2つの値を控える(新旧どちらのキー画面でも可):
   - **Project URL**: Settings → **Data API** に表示される `https://xxxx.supabase.co`
   - **Secret key**: Settings → **API Keys** → 下段「Secret keys」の default(`sb_secret_...`)。
     目のアイコンで表示してコピー。★秘密の値
   - ※旧方式の画面の場合は、Project URL と `service_role` キーが同じ役割
   - ※上段の Publishable key(`sb_publishable_...` = 旧 anon)は使わない

### 8-2. Render の環境変数(約5分)

`maido-crafts-website` → **Environment** に追加して **Save, rebuild, and deploy**:

| Key | 値 |
|---|---|
| `SUPABASE_URL` | 8-1のProject URL |
| `SUPABASE_SERVICE_ROLE_KEY` | 8-1のSecret key(`sb_secret_...`。旧方式なら service_role)(★秘密) |
| `ADMIN_PASSWORD` | 管理画面のパスワード(長いものを) |
| `ANALYZE_SECRET` | 長い乱数(RenderのGenerateでよい) |
| `ANTHROPIC_API_KEY` | https://console.anthropic.com で発行(未設定でも数値レポートは動く) |
| `REPORT_TO` | (任意)週次レポートの宛先。未設定なら CONTACT_TO と同じ |

### 8-3. GitHub Actions の secrets(約3分)

リポジトリ → **Settings → Secrets and variables → Actions** に追加:

| Name | 値 |
|---|---|
| `ANALYZE_URL` | `https://<公開URL>/api/analyze` |
| `ANALYZE_SECRET` | 8-2と同じ値 |

→ 以後、毎週月曜9時(JST)に自動分析。**Actions → weekly-analysis → Run workflow** で手動実行も可

### 8-4. 動作確認

1. 公開サイトを数ページ閲覧し、LINEボタンを1回タップ
2. `https://<公開URL>/admin/` にログイン → 数値が出ていれば計測OK
3. Actions から weekly-analysis を手動実行 → 管理画面にレポートが出て、メールが届けば全経路OK

## 9. 実装メモ

- 計測が無効(環境変数未設定)でもサイトは通常どおり動く(ビーコンは204で空振り)
- 管理画面(/admin)自身の閲覧・ボットUAは計測から除外済み。robots/sitemapからも除外
- A/Bの配信バリアントは body の data 属性 → ビーコン meta 経由で全イベントに紐づく
- 週次分析: 統計判定(z検定・95%・各案100訪問以上)で勝者確定→ab_configを自動更新。90日超の明細も同時に削除
- AI分析には本リポジトリの規範(価格非掲載・実績創作禁止・トーン)をシステムプロンプトで注入している
